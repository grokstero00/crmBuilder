# crmbuilder

Конфигурация портала Битрикс24 как код. Портал описывается YAML-спецификацией,
а сервис приводит живой портал в соответствие с ней: импорт → план → применение →
откат. Поверх этого ядра будет работать ИИ-агент, который превращает ТЗ в правки
спецификации.

## Что уже есть

- `crmbuilder import` читает портал через входящий вебхук и пишет:
  - `portal.yaml`: спецификация (воронки и стадии сделок, пользовательские поля
    лидов, сделок, контактов и компаний, смарт-процессы с воронками и стадиями,
    структура отделов);
  - `portal.state.json`: связь ключей спецификации с ID в Битриксе
    (`C1:NEW`, `UF_CRM_1712345678`, ID воронок и отделов).

  Если state-файл уже есть, повторный импорт сохраняет прежние ключи, даже если
  объекты переименовали на портале. `--fresh` генерирует все ключи заново.
- `crmbuilder plan portal.yaml` заново читает портал и показывает, что нужно
  изменить, чтобы он совпал со спецификацией. На портале ничего не меняется.
  `--json` выводит план для программ, `--against other.yaml` сравнивает два файла
  без обращения к порталу.
- `crmbuilder apply portal.yaml` меняет портал так, чтобы он совпал со спецификацией.
- `crmbuilder rollback portal.yaml` возвращает портал к состоянию до последнего `apply`.
- `crmbuilder template list` / `crmbuilder template add clinic portal.yaml` вливает
  готовый набор настроек (шаблон) в спецификацию. Шаблон только добавляет объекты
  с новыми ключами и ничего не удаляет; портал не трогается до `apply`.
- `crmbuilder design portal.yaml --brief tz.md` — ИИ-проектировщик: Claude читает ТЗ и
  текущую структуру портала, при необходимости задаёт вопросы и правит спецификацию.
  Портал не трогается; дальше обычные `plan` и `apply`.
- `crmbuilder validate portal.yaml` проверяет спецификацию по схеме.

## ИИ-проектировщик: design

```bash
docker compose run --rm -T cli design sandbox/portal.yaml --brief tz.md
docker compose run --rm -T cli design sandbox/portal.yaml --brief-text "Добавь воронку тендеров"
```

- Нужен `ANTHROPIC_API_KEY` в `.env` (console.anthropic.com). Модель по умолчанию —
  Claude Opus 5.5, `--model claude-sonnet-5-5` вдвое дешевле.
- Claude меняет спецификацию только инструментами create / update / delete по
  адресам из плана. Каждая правка проверяется схемой; неверная откатывается, и модель
  получает ошибку. Смарт-процессы, роботы, права и т. п. модель не создаёт, а выносит
  в «ручные шаги» в итоговом ответе.
- Вопросы задаются в консоли, Enter оставляет решение модели. `--no-questions` —
  работать на допущениях.
- В конце: итог от модели, расход токенов и примерная стоимость, план изменений и
  вопрос, сохранять ли файл. Портал меняет только `apply` со всеми предохранителями.
- В модель уходит только структура портала (названия, ключи, типы), без данных CRM.
- Если отказ модели связан с её фильтрами безопасности, запрос автоматически
  повторяется на рекомендованной Anthropic резервной модели (`fallbacks: "default"`).

## Применение изменений: apply и rollback

`apply` — единственная команда, которая пишет в портал. Предохранители:

1. **Разрешение в `.env`.** Без `BITRIX_ALLOW_WRITE=yes` команда откажется работать,
   даже не обращаясь к порталу. Для рабочих порталов клиентов не включайте.
2. **Всё или ничего на этапе проверки.** Если в плане есть изменение, которое
   Битрикс не умеет делать (сменить группу стадии, сделать новую воронку основной)
   или которое пока не поддерживается (создание и правка самих смарт-процессов),
   ничего не применяется.
3. **Опасные изменения** (удаление, пересоздание поля) требуют флага
   `--allow-destructive`.
4. **Подтверждение:** нужно ввести имя портала. `--yes` пропускает этот шаг.
5. **Снимок и журнал:** перед изменениями в `.history/<время>/` рядом со
   спецификацией сохраняются портал «до», план и журнал всех вызовов API.
6. **Остановка при ошибке:** первая ошибка Битрикса останавливает применение,
   state-файл описывает то, что реально сделано.
7. **Проверка:** после применения портал перечитывается и сравнивается со
   спецификацией.

Битрикс сам не даёт удалить воронку со сделками и стадию, в которой есть
элементы: такие ошибки остановят `apply`, данные не пострадают.

`rollback` применяет снимок «до» последнего `apply` (или `--to <снимок>`) с теми же
предохранителями. Он восстанавливает **структуру**, но не данные: если поле было
удалено, оно создастся заново пустым.

```bash
# Git Bash: подтверждение можно ввести с клавиатуры или передать через echo
docker compose run --rm -T cli apply test/portal.yaml
echo test-portal.bitrix24.ru | docker compose run --rm -T cli apply test/portal.yaml
docker compose run --rm -T cli rollback test/portal.yaml
```

## Рабочий цикл

```bash
crmbuilder import -o clinic/portal.yaml   # 1. прочитать портал
# 2. поправить clinic/portal.yaml
crmbuilder plan clinic/portal.yaml        # 3. посмотреть, что изменится
```

Пример плана:

```
Plan for clinic.bitrix24.ru

  ~ update  crm.deal_categories.obshchaya.stages.prepayment_invoice
        name: "Cчёт на предоплату" -> "Счёт на предоплату"
  + create  crm.deal_categories.obshchaya.stages.peregovory
        name: "Переговоры"
        semantic: "process"
        sort: 55
  - delete  crm.fields.deal.tip_printera
        WARNING: data stored in this field will be lost

Plan: 1 to create, 1 to update, 1 to delete.
1 destructive change(s) marked with - or ! can lose data.
```

Объекты сопоставляются по ключу: новый ключ в файле означает создание, пропавший
ключ означает удаление. Поэтому переименовывать ключи нельзя, меняйте
`name`/`label`. Тип поля и флаг множественности Битрикс менять не умеет, такие
правки план показывает как `replace` (удалить и создать заново, данные теряются).

Ссылки CRM-полей на смарт-процессы хранятся по ключу (`SMART_PROCESS:vebinary`),
а не по номеру `DYNAMIC_1066`, поэтому спецификацию можно переносить между
порталами. Настройки полей, совпадающие со значениями Битрикса по умолчанию,
в файл не пишутся.

## Пример спецификации

```yaml
version: 1
portal: clinic.bitrix24.ru
crm:
  deal_categories:
    - key: pervichnyy_priem
      name: Первичный приём
      stages:
        - {key: new, name: Новая заявка}
        - {key: zapisan, name: Записан}
        - {key: won, name: Пришёл, semantic: success}
        - {key: lose, name: Не пришёл, semantic: failure}
  fields:
    deal:
      - key: doctor
        label: Врач
        type: employee
        required: true
```

В спецификации нет ID Битрикса, только стабильные ключи. Ключи берутся из кода
объекта (`UF_CRM_DOCTOR` → `doctor`, `C1:NEW` → `new`), а для автосгенерированных
кодов (`UF_CRM_1712345678`, `UC_X7K2P1`) — из транслитерированного названия.
Сами ID хранятся в state-файле.

## Запуск в Docker

```bash
cp .env.example .env          # вписать BITRIX_WEBHOOK_URL
docker compose build
docker compose run --rm cli import -o clinic/portal.yaml
docker compose run --rm cli plan clinic/portal.yaml
```

Файлы появятся в `./workspace/clinic/`.

Вебхук создаётся в портале: «Разработчикам» → «Другое» → «Входящий вебхук».
Права: `crm` и `department` (структура компании). Импорт только читает данные.

### Windows (Git Bash + Docker Desktop)

Команды те же, что выше, с несколькими отличиями:

- Docker Desktop должен быть запущен (значок кита в трее). Проверка: `docker version`.
- `HOST_UID` и `HOST_GID` в `.env` оставьте `1000`. Не подставляйте вывод `id -u`:
  в Git Bash он выдаёт виндовый номер вроде `197609`, который здесь не нужен.
- `.env` удобно править так: `notepad .env`.
- Если `docker compose run` пишет `the input device is not a TTY`, добавьте флаг `-T`:
  `docker compose run --rm -T cli import -o test/portal.yaml`.
- Результат открывается в Проводнике командой `explorer workspace`.

### Ошибка SSL (CERTIFICATE_VERIFY_FAILED)

Программа в контейнере не доверяет сертификату портала. Частые причины: антивирус
(Касперский, ESET, Dr.Web) или корпоративный прокси проверяет HTTPS и подставляет
свой сертификат; либо сайт подписан национальным УЦ, которого нет в стандартном
наборе. Проверку сертификатов программа не отключает: через соединение передаётся
ключ вебхука.

1. Узнайте, кто выдал сертификат (Git Bash):
   `openssl s_client -connect <портал>:443 -servername <портал> </dev/null 2>/dev/null | grep -A1 "^ 0 s:"`
   Строка `i:` — издатель.
2. Экспортируйте его корневой сертификат в формате Base-64 (PEM):
   Windows → `certmgr.msc` → «Доверенные корневые центры сертификации» → найдите
   издателя → «Все задачи» → «Экспорт» → «Файлы X.509 (.CER) в кодировке Base-64».
3. Сохраните файл как `workspace/ca.pem` и добавьте в `.env`:
   `BITRIX_CA_BUNDLE=/workspace/ca.pem`

Сертификат добавляется к стандартным, а не заменяет их.

## Локальная разработка

```bash
uv venv && uv pip install -e '.[dev]'
.venv/bin/pytest
.venv/bin/ruff check . && .venv/bin/ruff format --check .
```

Тесты не ходят в сеть: Битрикс эмулируется через `httpx.MockTransport`
(`tests/conftest.py`).
